# 审查要求

1. 只指出**真实问题**，属于以下几类：bug、安全漏洞、数据丢失或损坏、并发问题、错误处理缺失、明显性能问题、明显的可维护性问题。
2. 不评论纯风格偏好（缩进、引号风格、命名口味、与本项目惯例无关的格式问题），不复述或总结改动内容，不为凑数而报告问题。**没有问题时，findings 必须返回空数组 `[]`**，并在 summary 里说明未发现明显问题。
3. 只评论本 diff 中**新增或修改的行**（diff 中前缀为 `+` 的行）。你可以用 Read / Grep / Glob 工具查看仓库里的其他文件来确认上下文（例如被调用函数的实现、常量的定义），但每条问题的 `line` 必须落在本 diff 的新增行上；纯删除的行和 diff 之外的行不评论。
4. `file` 必须与 diff 中「### 文件: 」后给出的路径完全一致；`line` / `endLine` 必须取自 diff 每行行首标注的**新文件行号**，不要自己推算，不要用旧文件（删除侧）行号。
5. 严重度定义（从高到低，只能取这四个值之一）：
   - `blocker`（严重）：必须修复，否则不能合并。会在常见场景下导致数据丢失/损坏、安全漏洞、崩溃或明确的功能错误。例：把用户数据整个覆盖掉、SQL / 命令注入、未处理的空值导致崩溃、权限校验被跳过。
   - `major`（重要）：应当修复，很可能在常见场景下引发错误或明显劣化。例：异常被静默吞掉导致难以排障、循环边界 off-by-one、并发读写同一文件未加锁、资源泄漏。
   - `minor`（一般）：明确但影响有限的问题。例：缺少输入校验但有上层兜底、循环里重复编译同一正则、错误信息缺少定位上下文、竞态窗口极小且后果轻微。
   - `nit`（建议）：可选的小改进，不修也可以。例：更清晰的命名、重复两三行的代码可提取、注释与实现略有出入。
6. `title` 不超过 60 字，一句话说清「哪里有什么问题」；`body` 不超过 800 字，说明问题的原因与影响，必要时引用相关代码；`suggestion` 给出建议的替换代码片段（只在确实有明确改法时提供，可省略）。
7. 所有输出（summary、title、body、suggestion）都用**中文**撰写（代码与专有名词除外）。

# 输出格式

只输出**一个 JSON 对象**，不要输出任何其他文字，不要用 markdown 代码块包裹，不要添加注释：

```json
{
  "summary": "整体评价，一到两句话",
  "findings": [
    {
      "severity": "blocker | major | minor | nit",
      "file": "src/example.ts",
      "line": 12,
      "endLine": 14,
      "title": "一行标题",
      "body": "问题的原因与影响",
      "suggestion": "建议的替换代码"
    }
  ]
}
```

字段说明：

- `summary`：必填，字符串；没有问题时说明「未发现明显问题」。
- `findings`：必填，数组；**没有问题就是空数组**。
- `severity` / `file` / `line` / `title` / `body`：每条问题必填。
- `endLine`：可选，问题范围的最后一行，必须与 `line` 在同一个 hunk 内且 ≥ `line`；单行问题省略它。
- `suggestion`：可选，仅在有明确替换代码时提供。
